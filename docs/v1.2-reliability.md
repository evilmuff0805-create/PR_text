# V1.2 변환 안정성

## 변경
- 일반 변환을 별도 영속 작업으로 접수한다. 사용자별 작업 키와 원본·언어 해시를 확인해 같은 작업을 재접수해도 결과와 차감을 중복 확정하지 않는다.
- 원본은 재인코딩하지 않고 최대 40MiB 조각으로 비공개 저장한다. 작업자가 전체 길이와 SHA-256을 검증한다.
- 처리 결과 체크포인트, 변환 이력, 예약 소비, 사용 기록, 완료 상태를 안전하게 저장한다. 체크포인트 이후 저장 재시도에서는 전사를 다시 호출하지 않는다.
- 새로고침·로그인 복귀·접수 응답 유실 때 작업 키로 복구한다. 완료 키도 다음 새 변환까지 보존한다. 미확인 작업을 새 키로 덮어쓰지 않는다.
- 취소와 완료는 DB 잠금으로 한쪽만 확정한다. 반환은 기존 FEFO·결제 취소·만료 정책을 따른다. 계정 탈퇴는 staged 작업까지 보호한다.
- 기존 다화자 처리, 자막 편집·형식, 영어 타이밍 처리, OAuth, 검색용 공개 HTML은 유지한다. 랜딩은 V.1.2로 표시한다.

## 운영 범위
- `TRANSCRIPTION_OPERATIONS_ENABLED=true`일 때만 신규 v2 접수를 활성화한다. 누락/false이면 기존 경로로 처리한다. 작업자와 원본 정리는 플래그와 무관하게 계속 실행한다.
- 파일 길이를 읽지 못한 형식은 기존 동기 변환으로 처리한다. 이 예외 경로와 오래 캐시된 구버전 클라이언트는 새 작업 복구 보장을 받지 못한다.
- 일반 작업자는 인스턴스당 1개다. 사용자별 미완료 작업은 최대 3개다. 이는 안정성·메모리 제한이며 처리 속도 개선을 뜻하지 않는다. 기존 약 103초 처리 사례를 단순 적용하면 3건 중 마지막 완료는 약 5분 후로 예상되며, 실제 부하 성능 측정값은 아니다. `transcription.operation.claimed.queueAgeMs`로 대기를 관찰한다.
- 작업 회수는 최대 3차례 전사 시도를 허용한다. 기존 SDK 재시도·분할 요청은 별도이므로 공급자 호출 전체가 3회라는 뜻이 아니다. 공급자 응답과 DB 연결이 동시에 사라지면 외부 호출 비용이 중복될 수 있으나 사용자 완료·차감은 한 번만 확정한다.
- staged/queued 접수는 24시간 뒤 정리·취소한다. 완료/실패/취소 원본은 정리 작업이 삭제하며, 탈퇴 뒤 늦게 남은 고아 원본은 24시간 이후 정리한다. 원본 삭제 실패는 재시도한다. 결과와 작업 키는 계정 삭제 전까지 유지한다.

## 검증
- 기존 회귀와 신규 장애 주입 테스트: `npm test`.
- 빌드: `npm run build`.
- 실제 PostgreSQL 17에서 전체 마이그레이션 재생, 16개 정산/권한/복구 시나리오, 9개 실제 다중 연결 경쟁/정합성 시나리오.
- GitHub CI의 `database-regressions`가 임시 PostgreSQL 17에서 위 검사를 매 PR마다 실행한다. 테스트 DB는 운영과 분리하며 합성 사용자만 사용한다.
- 로컬 수동 DB 검사: 별도 PostgreSQL 17과 `pg` 클라이언트를 준비하고 `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PG_CLIENT_PATH`를 테스트 전용 값으로 지정한 뒤 `node scripts/validation/db-operations.cjs`와 `node scripts/validation/db-concurrency.cjs`를 실행한다. DB 생성 권한이 필요하다. 이 명령을 운영 DB에 연결하지 않는다.
- 격리된 Chrome에서 토큰 없는 랜딩, 모바일 가로 넘침, 새로고침 복구, POST 응답 강제 유실, 같은 결과 복구, 새 변환 키 분리를 확인했다. 인증/공급자는 합성 응답으로 재현했으며 실제 고객 음원을 재전사하지 않았다.

## 배포와 복구
1. 확장 마이그레이션을 먼저 적용한다. 기존 진행 작업과 원장 정합성을 확인한다.
2. 새 코드를 기능 플래그 OFF로 배포해 건강 상태·화면·권한 차단을 확인한다.
3. Railway의 해당 서비스에서 `TRANSCRIPTION_OPERATIONS_ENABLED` 하나만 true로 설정하고 새 배포를 확인한다. 관계없는 대기 설정 변경은 일괄 적용하지 않는다.
4. 문제 시 신규 접수 플래그만 false로 되돌리고 작업자와 새 스키마를 유지해 이미 접수된 작업을 마무리한다. 작업이 남아 있는 상태로 스키마를 삭제하거나 구버전 작업자로 교체하지 않는다.
