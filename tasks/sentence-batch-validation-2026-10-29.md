# 문장 다듬기 묶음 축소 검증

## 결론

문장 다듬기의 요청당 문맥 그룹 수를 12개에서 6개로 줄였다. 이번 실제 API 비교에서 12개 방식은 4회 중 응답 형식 오류 2회·시간 초과 1회, 6개 방식은 추가 확인을 포함해 5회 모두 처리 오류 없이 끝났다. 작은 표본의 관측 결과이며 서비스 전체의 무오류를 보장하지 않는다.

기존 원문 유지 모드의 처리·모델·프롬프트는 그대로다. 배포 및 운영 변경은 하지 않았다. 가사처럼 인식 원문 자체가 불확실한 입력에서는 의미를 바꿀 수 있는 수정이 여전히 발견돼, 포괄적인 품질 보장 및 출시 승인은 보류한다.

## 변경과 보호

- 요청당 문맥 그룹 12→6. 한 문맥 그룹 내부 최대 12개 자막은 쪼개지 않는다.
- 기존 파일당 120개 자막/3,360자, 배치의 생성+검수 합계 30초, 파일 전체 60초 제한 유지.
- 모델·프롬프트·자동 재시도·병렬 처리·기본 변환 경로 불변. 실패 전 성공한 배치는 유지하고 실패/미처리 구간은 원래 결과로 보존한다.
- 실제 평가에서 격식체가 해요체로 바뀐 사례를 확인해, 명백한 격식 종결을 낮추는 후보를 코드로 거부하도록 추가했다. 해요체·반말의 모든 세부 말투까지 보장하는 검사는 아니다.

## 비교 방법

기존 승인된 키와 gpt-6-luna를 사용했다. 합성 20문장(개선 대상 8개·보호 대상 12개), 사용자 제공 대화 29.5초·노래 189.88초의 **동일한 저장 전사/맞춤법 결과**에 문장 다듬기만 추가했다. 이번에는 음원 전사를 다시 호출하지 않았다. 기존 12개 방식은 변경 전 서비스 함수 사본을 사용했고, 6개 방식과 처음에는 묶음 상수만 다른 것을 확인했다. API 호출은 겹치지 않게 순차 진행했으며 합성 두 번째 회차는 6→12 순서로 바꾸었다. 모든 실패 결과를 포함했다.

## 실제 API A/B 결과

12개 방식의 형식 오류는 원래 두 줄이어야 할 문맥을 한 줄로 반환한 경우였다. 잘못된 결과는 적용하지 않았다. 6개 방식은 이번 표본에서 처리 성공률이 높았지만 호출 수와 토큰은 늘었고 합성 입력은 더 오래 걸렸다. 실패해 빨리 끝난 요청과 정상 완료 시간을 단순 속도 향상으로 비교하지 않는다.

격식체 보호를 추가한 최종 코드로 합성을 한 번 더 실제 호출했다: **34.006초, 6회 호출, 6,015토큰, 7개 수정, 처리 오류 없음**. 개선 대상 8문장 중 7문장에서 자연스러운 호응·중복 정리가 확인됐고 보호 대상 12문장은 유지됐다. 모델 비결정성으로 회차별 결과는 달라진다.

## 품질과 시간

- 합성 첫 회차는 개선 대상 5/8개 개선과 보호 대상의 구두점 2개 수정이었다. 두 번째 회차의 격식체 변경 1건은 최종 보호 검사로 거부했다. 저장된 실제 API 응답을 최종 코드에 재생해 10→9개 수정(개선 대상 7개·구두점 2개)으로 줄어드는 것을 확인했다. 재생 검증은 신규 API 호출과 구분한다.
- 대화 3개 수정은 쉼표·띄어쓰기·조사 보완이며 큰 문장 재작성 효과로 과장하지 않는다.
- 노래 2개 수정은 원문 단어를 다른 단어로 추정한 사례다. 독립 음성 입력 모델에 후보를 보여주지 않고 대조했으나 불일치/빈 응답으로 가사를 확증하지 못했다. **품질 개선 건수에서 제외하며 의미 변경 위험이 남는다.** 잘못 인식된 가사를 문장 교정만으로 신뢰성 있게 복구한다고 주장하지 않는다.
- 모든 A/B 실행·최종 추가 실행·최종 보호 검사 재생에서 표시 자막 시간/화자와 SRT·ASS 시각은 동일했다. 짧은 공백 유지 옵션 양쪽을 확인했다.
- 사람의 원음 청취·프리미어 반입·프레임별 실싱크 검증은 하지 않았다. 시간값 보존과 실제 발화 대응의 정확성은 구분한다.

## 남은 위험
